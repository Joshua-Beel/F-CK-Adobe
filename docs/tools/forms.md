# Fill existing fields

Open a PDF and choose **Fill forms** from All tools or the quick toolbar. The dialog lists the fields that this build can safely preserve. Change a text value or checkbox, then choose **Save filled copy**. Windows asks where to save the output; the open source PDF, its dirty state, and its undo history remain unchanged. The new file opens as a clean tab.

This is a small compatibility slice, not Fill & Sign. Text values accept printable ASCII only and are checked against both a field's character limit and its existing layout before the native operation runs. The native layer checks again before saving. It supports only flat, visible, single-line text fields with one widget, a validated fixed Helvetica style, a fixed supported font size, solid border, and supported gray or RGB colors. A populated text field must also have a compatible normal appearance; a blank text field can omit one only when its remaining validated style is sufficient. It also supports flat merged square checkbox fields, each with Off and one matching on state across its normal and any rollover or down appearances. Their bounded vector-only artwork cannot use fonts, images, or transforms, and the source styles remain intact rather than being replaced with a uniform check shape. The checkbox's source state name remains internal; the dialog shows only its source field name, page, and checked state. Radio buttons, signature controls, and other button groups are unavailable. Unsupported fields, actions, signatures, XFA, encryption, unknown appearance/layout content, non-ASCII input, overflow, or an edited page plan make the whole form unavailable or reject the attempted copy. There is no partial fill.

The original document's crop and rotation are preserved. A crop can therefore hide or clip a listed source field: it remains fillable, but this tool does not expand the crop, remove the field, or promise that the saved value is visible on the cropped page or printout.

The form has at most 256 text fields and checkboxes together. A text value is limited to 4 KiB and all field names and values to 1 MiB; the native layer also bounds source parsing, appearance decoding, and serialized output. These are compatibility and output guards, not a memory-use claim.

There is no in-place form editing, form preparation, certificate workflow, handwriting, signature placement, author identity, radio-button editing, or general Acrobat form support. Canceling the native save dialog or receiving a native error keeps the dialog's entries so they can be corrected or retried.

The mixed-field source gate passed 151 frontend/release tests and 123 native tests with one ignored manual probe, the production frontend build, and a standalone Tauri Windows debug/no-bundle build. The focused checkbox gate passed 7 tests, and the earlier text-field regressions remain green. Native checks cover a ReportLab compatibility fixture with independent pypdf/Poppler inspection, local and inherited crop/rotation, changed-field pixels and values, custom checkbox on states, retained checkbox appearances/defaults, immutable print snapshot bitmaps, source/reopen preservation, every original page across the three corpus fixtures with an appended independent form page, and receiver/ownership guards. This is evidence for that strict subset, not broad cross-viewer form compatibility. Focused UI tests cover changed-only tagged patches, printable-ASCII and size checks, keyboard checkbox input, false/blank/reverted values, unsupported forms, cancellation/error draft retention, duplicate-submit and Escape guards, a stale query response, and opening a clean output tab without changing a dirty source tab. A Vite browser harness uses mocked IPC to check a keyboard checkbox patch and cancellation draft behavior. Native desktop save-dialog interaction and installed-app behavior remain separate work.
